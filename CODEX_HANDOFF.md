## Projectile emission research (2026-10-28; research only — no code change)

- Research-only turn; no source/test/build change, suite stays **91/91** (last `build/straight-specials-tests.log`, 310.83s). New read-only audits `build/mapping-research/audit_bullet_enable_scan.py` and `audit_bullet_enable_crosstab.py` scanned the full 506MB recovered archive (15,078 clips, 832 with type-2 events, **2,106 BulletBehavior events**) to settle the recurring `Enable` question. Findings in `build/projectile-emission-research.log`.
- **`Enable` is a real bimodal field, not a stale default**: 98 True vs 2008 False. Enable=True events are always Offset=0 (98/98) and StateInfo=0 (98/98), mostly Unk12=255 (72/98), and concentrate in pure-projectile categories (a902 16/16, a934 43/43, a370 6/6, a671/a772/a795/a802/a804/a806/a847/a956/a969 all-True) — spells/throws/bows. Enable=False events spread Offset 0/1/2 and include StateInfo-gated tail (412/469/484/485). Conclusion: `Enable` marks emission CONTEXT (standalone vs weapon-swing-attached), not emission YES/NO; it does not mean "disabled".
- **Martial-art Enable=False bullets demonstrably emit and deal damage**: a55/anim-030500 carries type-1 melee judges 105+106 alongside type-2 bullet judge 107 (Enable=False -> AtkParam 6300107, MV 135), matching the community sheet's "150 (135 Bullet)" exactly. Dane's Footwork's blade-wave normal attacks are these Enable=False type-2 events in a246. So Enable=False does not suppress emission.
- **Leaf single-contact model is now fully evidenced**: all 54 martial-art bullets are leaf (numShoot=1, shootInterval=0, no child, isEndlessHit=0; `complex links []`); uniform params life=0.1 = dmgHitRecordLifeTime=0.1, dist=0, five damping=90, isUseSharedHitList=1, launchConditionType=0, SpEffects=0; isPenetrateChr/Map/Obj=1. One event = one projectile = at most one contact per target (0.1s hit-record immunity equals 0.1s life) at the linked AtkParam MV; dist=0/life<1s make damping moot at native values. Multiple events = multiple instances (a55/32510 has two 160-MV events, matching sheet "160 + 160 Bullets"). All Source=0 (evaluated weapon), same as direct melee — no secondary-weapon ambiguity.
- Residual unknowns stated explicitly: `Enable` runtime meaning is inferred from distribution + cross-checks, not read from the game binary/HKS; a general projectile policy would still need dist/damping and shared-hit-volley modeling, which are moot only for these leaf bullets. No native code reads back the exact emission condition.
- **Recommendation (not implemented)**: the importer already rejects non-leaf emission and stores bulletParamId + bulletParameters for surviving leaf bullets; the only blocker is calculator `hit_uses_secondary_weapon` rejecting any bullet-typed hit. A bounded admission would score an audited leaf bullet exactly like a Source-0 direct hit at the linked AtkParam MV (no new moveset shape, no per-weapon exceptions), still rejecting non-leaf/StateInfo-gated/non-uniform-life bullets. Decision deferred to maintainer. Dane's Footwork remains excluded this turn.

## Architecture and unresolved mechanics
- Existing OO design: `Weapon` owns `shared_ptr<Moveset>`, `Moveset` contains named `Move`s and ordered `Hit`s. Reuse/share resolved movesets for weapons with equivalent data. User's existing reflection system handles shared_ptr; **do not rebuild serialization**.
- Each `Hit` should preserve all 12 MV channels, per-hit animation-relative `double startTime/endTime`, animation ID, TAE event type, behavior judge ID, behavior row ID/category, AtkParam ID, AttackIndex, raw Source and possibly resolved hand.
- Some animations contain repeated/multiple attack events. Never assume 1 input = 1 hit or dedup by judge. TAE type 307 events are not automatically damage events. Treat start/end as *scheduled hit activation windows*, not confirmed contact frames.
